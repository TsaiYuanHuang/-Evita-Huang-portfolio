建置 PM 專案需求評估 AI Agent

Building a PM Project Requirement Assessment AI Agent

將設計中心散落在專案筆記、會議記錄與 SOP 中的需求評估經驗，結構化為關鍵字庫、檢核庫與角色表，並導入公司內部 AI 平台——讓不同資歷的 PM 在需求前期，都能快速掌握重點、風險與待確認事項。

Structured the requirement-evaluation experience scattered across project notes, meeting records and SOPs into a keyword library, checklist library and role table, then deployed it on the company's internal AI platform — so PMs of any seniority can quickly see key points, risks and open questions at the start of a request.

專案背景Context

每封需求信，都要重新判斷一次「哪裡要注意」

Every Request Email Means Re-judging "What to Watch For"

友達設計中心的專案橫跨車載、AR 眼鏡、醫療、零售與展會活動，需求來自不同的需求單位，內容與限制各不相同。要在收到需求的第一時間判斷「重點在哪、風險是什麼、還缺什麼資訊」，目前主要仰賴 PM 個人的經驗與記憶。

The Design Center's projects span in-vehicle systems, AR glasses, medical, retail and exhibitions, with requests coming from many requesting units, each with different content and constraints. Spotting the key points, risks and missing information the moment a request arrives relied mostly on individual PMs' experience and memory.

經驗存在個人腦中，資淺 PM 容易遺漏、資深 PM 也要花時間回想，需求對焦的前置作業因此被拉長。

Experience lived in individual heads, so junior PMs could miss things and senior PMs still spent time recalling — stretching the preparation before a request is aligned.

我給自己的問題是：怎麼讓「經驗」變成一份誰都能查、AI 也能讀的資料？

The question I set myself: how do we turn "experience" into something anyone can look up and an AI can read?

資料庫設計Database Design

以三層專案架構，整理成三張工作表

A Three-layer Project Framework, Organized into Three Sheets

依據歷史專案筆記、會議與 SOP、部門名詞表，我把需求拆成三個層級，再加上需求單位與通用類別，讓任何一封需求信都能被對回標準關鍵字：

Drawing on historical project notes, meeting records, SOPs and the department glossary, I broke requests into three layers, plus requesting units and a general category, so any request can be mapped back to standard keywords:

L1

設計內容與產出

Design Content & Deliverables

ID、UX、UI、Animation，以及 KV、Teaser、Rendering 等交付物——對應「要做什麼設計」。

ID, UX, UI, Animation, plus deliverables such as KV, Teaser and Rendering — "what design is needed".

L2

產品與技術

Product & Technology

產品類型與技術限制（Placement、Dimension、Lens、FPC、法規等）——對應「針對哪一種產品設計」。

Product types and technical constraints (placement, dimension, lens, FPC, regulations…) — "which kind of product it is designed for".

L3

使用情境

Usage Scenario

展會、Showroom、Customer Demo、POC、Proposal——對應「用在哪裡」，決定時程與交付形式。

Exhibitions, showrooms, customer demos, POCs and proposals — "where it is used", which drives schedule and delivery form.

工作表 01Sheet 01

關鍵字庫（辨識層）

Keyword Library (Recognition)

把信中各種寫法對回標準關鍵字，並標明所屬層級。

Maps the many ways a request is worded back to a standard keyword and its layer.

工作表 02Sheet 02

檢核庫（知識層）

Checklist Library (Knowledge)

每列是「某個關鍵字出現時要注意的一件事」：類型（重點／風險／待確認）、現象 → 影響、可直接詢問的問題、嚴重度。

Each row is one thing to watch for when a keyword appears: type (key point / risk / to-confirm), cause → impact, a ready-to-send question and severity.

工作表 03Sheet 03

角色表（指派層）

Role Table (Assignment)

把「該找誰確認」對應到角色與負責範圍，不綁定人名，方便長期維護。

Maps "who to ask" to roles and scopes of responsibility — no personal names, so it stays maintainable.

跨領域覆蓋Domain Coverage

一套框架，涵蓋 17+ 種產品類型、7 大領域

One Framework, 17+ Product Types Across 7 Domains

入職後我同步補足各需求單位的產品與技術知識，並把它們寫進資料庫，讓 Agent 不只知道「有哪些詞」，也知道「這個詞背後要注意什麼」。

After joining, I built up product and technical knowledge across the requesting units and wrote it into the database, so the agent knows not just which terms exist but what each of them implies.

On the design side it covers ID, UX, UI, animation and commercial design; on the usage side, exhibitions, showrooms, customer demos and proposals — one database linking hardware mechanisms to software interfaces.

驗證與迭代Validation & Iteration

用新的需求資料，找出資料庫的缺口

Using a New Request to Find Gaps in the Database

資料庫做好後，我拿一份全新的需求資料來測試：在不修改檔案的前提下，檢視現有關鍵字與檢核項目無法涵蓋之處，共提出 5 個新關鍵字與 10 列新檢核項目。

Once the database was built, I tested it with a brand-new request: without editing the file, I checked what the existing keywords and checks failed to cover, which surfaced 5 new keywords and 10 new checklist rows.

這個流程確保資料庫易於擴充，也讓日後維護有明確可行的做法：每一份新的需求，都是一次補強資料庫的機會。

This loop keeps the database easy to extend and gives future maintenance a clear, practical routine: every new request is a chance to strengthen it.

Agent 導入AI Agent Deployment

在公司內部 AI 平台，建置「專案需求評估助理」

Building the "Project Requirement Assistant" on the Internal AI Platform

資料留在 ExcelLM，規則放在 Digital Entity，流程放在 Skill。需求信進來後，Agent 依資料庫比對、撈取、指派，輸出可直接使用的分析：

Data stays in ExcelLM, rules live in the Digital Entity, and the process lives in a Skill. When a request arrives, the agent matches, retrieves and assigns against the database and outputs a ready-to-use analysis:

Agent 的行為規範

Guardrails Built into the Agent

  • 只使用資料庫查得到的內容，查不到就明說，不自行編造風險
  • Uses only what the database contains; says so when nothing matches instead of inventing risks
  • 引用信中原句作為「已知資訊」，方便 PM 抽查
  • Quotes the original sentence for each "known" item so PMs can spot-check
  • 每個風險與問題附檢核庫 ID，可回查來源
  • Every risk and question carries a checklist ID for traceability
  • 發現資料庫缺口時，建議新增內容，由 PM 決定是否回填
  • Flags database gaps and suggests additions; the PM decides what to add back
設計決策Design Decisions

三個關鍵決策

Three Key Decisions

決策 01Decision 01

把隱性經驗結構化，再導入 Agent

Structure Tacit Experience First, Then Automate

先把「PM 腦中的判斷」拆成可填寫的欄位（現象 → 影響、可問的問題、找誰、嚴重度），再交給 AI。Agent 的品質取決於知識的品質，而不是 prompt 寫得多精巧。

Before handing anything to AI, I turned "what PMs know" into fillable fields (cause → impact, question to ask, who to ask, severity). The agent is only as good as the knowledge behind it, not how clever the prompt is.

決策 02Decision 02

設計成「通用版」，而非特定年度版

General-purpose, Not Tied to One Year

資料庫不寫年度日期與人名，改用角色與一般性描述，並以單一關鍵字庫搭配「層級」欄，降低日後擴充與填寫的負擔。

No dated or named entries — only roles and general descriptions — and a single keyword sheet with a "layer" column, keeping future expansion and data entry light.

決策 03Decision 03

為平台效能簡化流程

Simplify the Flow for Platform Performance

過於複雜的多重依賴流程在內部平台上會跑得較慢，因此 Skill 刻意只保留 3 個線性節點，必要時還能再合併。

Heavily interdependent workflows ran slowly on the internal platform, so the Skill deliberately keeps just 3 linear nodes, which can be merged further if needed.

反思Reflection
核心學習Key Learning
「PM 的經驗，不該只存在 PM 的腦中。」
"A PM's experience shouldn't live only in the PM's head."

從洞察知識庫到需求評估資料庫，在職涯中我不斷累積：把隱性知識轉譯為結構，讓它能被查詢、被傳承，也能被 AI 使用。不同的是，這次的使用者是每天面對需求的 PM，因此我更在意填寫的門檻與判斷的可追溯性。

From the insight knowledge base to this requirement-evaluation database, what I keep building throughout my career is the same thing: translate tacit knowledge into structure so it can be queried, passed on and used by AI. This time the users are PMs facing requests every day, so I paid closer attention to how easy it is to fill in and how traceable each judgment is.

未來若再優化：

If I were to iterate:

  • 建立使用成效指標，追蹤需求對焦時間與遺漏事項的變化
  • Establish metrics to track alignment time and missed items
  • 定期依結案專案回填檢核庫，並校準嚴重度
  • Regularly back-fill the checklist from closed projects and calibrate severity
  • 擴充更多需求單位與產品類型，進一步支援跨部門協作
  • Expand to more requesting units and product types to support cross-team collaboration
